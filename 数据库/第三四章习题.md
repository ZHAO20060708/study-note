## 3.2

假设给你一个关系 `grade_points(grade, points)`，它提供从 `takes` 关系中用字母表示的成绩等级到数字表示的得分之间的转换。例如，`A` 等级可被指定为对应于 4 分，`A-` 对应于 3.7 分，`B+` 对应于 3.3 分，`B` 对应于 3 分，等等。学生在某门课程（课程段）上所获得的绩点被定义为该课程段的学分乘以该生得到的成绩等级所对应的数字表示的得分。

给定上述关系和大学模式，用 `SQL` 写出下面的每个查询。为简单起见，你可以假设没有任何 `takes` 元组在 `grade` 上取 `NULL` 值。

**a. 根据 `ID` 为 `'12345'` 的学生所选修的所有课程，找出该生所获得的总绩点。**

```SQL
SELECT SUM(course.credits * grade_points.points) AS total_grade_points
FROM takes
JOIN course ON takes.course_id = course.course_id
JOIN grade_points ON takes.grade = grade_points.grade
WHERE takes.ID = '12345';
```

**b. 找出上述学生的平均绩点（Grade Point Average，`GPA`），即用总绩点除以相关课程学分的总和。**

```SQL
SELECT SUM(course.credits * grade_points.points) / SUM(course.credits) AS gpa
FROM takes
JOIN course ON takes.course_id = course.course_id
JOIN grade_points ON takes.grade = grade_points.grade
WHERE takes.ID = '12345';
```

**c. 找出每名学生的 `ID` 和平均绩点。**

```SQL
SELECT takes.ID, SUM(course.credits * grade_points.points) / SUM(course.credits) AS gpa
FROM takes
JOIN course ON takes.course_id = course.course_id
JOIN grade_points ON takes.grade = grade_points.grade
GROUP BY takes.ID;
```

**d. 现在假设某些成绩可能为空，重新考虑你对本习题前几问的回答。解释你的解决方案是否仍然有效，如果不行，请提供能够正确处理空值的版本。**

前三问的解决方案依然完全有效，不需要改代码。

原因很简单：`SQL` 里标准的 `JOIN`（也就是 `INNER JOIN`）在做相等比较时，`NULL = 任何值` 都会返回 `unknown` 并被过滤掉。  

当一条 `takes` 记录里的 `grade` 是空值（比如课还没结，或者成绩还没录入），`takes.grade = grade_points.grade` 这个连接条件就不成立。这条没成绩的记录会直接从结果集里消失。  

因此，没出成绩的课压根不会参与后面的 `SUM()` 聚合，它的学分既不会加进分子（总绩点），也不会加进分母（总学分）。这完全符合现实中计算 `GPA` 的逻辑：没成绩的课不影响当前的 `GPA`。

假设我们有一个关系 `marks(ID, score)`，并且希望基于成绩按如下方式为学生评定等级：如果 `score < 40` 则为 `F` 级；如果 `40 ≤ score < 60` 则为 `C` 级；如果 `60 ≤ score < 80` 则为 `B` 级；如果 `80 ≤ score` 则为 `A` 级。写出 `SQL` 查询完成下列操作：

       CASE
           WHEN score < 40 THEN 'F'

## 3.7

考虑 `SQL` 查询：

```SQL
select p.a1
from p, r1, r2
where p.a1 = r1.a1 or p.a1 = r2.a1
```

在什么条件下上述查询选出的 `p.a1` 值要么在 `r1` 中，要么在 `r2` 中？请仔细考察 `r1` 或 `r2` 可能为空的情况。

### 1. 查询执行机制分析

该查询的执行逻辑如下：

- `from p, r1, r2`：先计算 `p × r1 × r2` 的笛卡尔积。
- `where ...`：再筛选满足 `p.a1 = r1.a1` 或 `p.a1 = r2.a1` 的行。
- `select p.a1`：最后输出 `p.a1`。

关键点：只要参与笛卡尔积的任一关系为空，整个笛卡尔积就为空。

### 2. 考察 `r1` 或 `r2` 为空的情况

题目本意是选出 `p` 中“至少出现在 `r1` 或 `r2` 之一”的 `a1`。分情况讨论如下：

- 情况 A：`r1` 为空，`r2` 不为空。
    由于 `p × r1 × r2 = ∅`，查询结果为空。即使 `p.a1` 在 `r2` 中存在，也会被漏掉。

- 情况 B：`r2` 为空，`r1` 不为空。
    同理，笛卡尔积为空，所有本应由 `r1` 命中的 `p.a1` 都会被漏掉。

- 情况 C：`r1` 和 `r2` 都不为空。
    笛卡尔积可正常生成组合。此时 `p.a1` 只要在 `r1` 或 `r2` 中出现，就能通过 `where` 条件被选出。

- 情况 D：`r1` 和 `r2` 同时为空。
    目标集合本来就是空集，查询结果为空，结论在这个边界条件下恰好正确。

### 3. 结论

该查询要稳定、无遗漏地表达“`p.a1` 在 `r1` 或 `r2` 中”，需要满足：

- `r1` 非空；
- `r2` 非空。

> 注：若希望在任意情况下都安全正确，建议避免隐式笛卡尔积，改用 `IN` 或 `UNION`。例如：

```SQL
select a1 from p
where a1 in (select a1 from r1)
     or a1 in (select a1 from r2)
```

## 4.1

请考虑以下 SQL 查询，该查询旨在查找 2017 年春季讲授的所有课程的标题以及教师的姓名的列表。

```SQL
select name, title
from instructor natural join teaches natural join section natural join course
where semester = 'Spring' and year = 2017
```

请问这个查询有什么问题？

这个查询的主要问题在于 `natural join` 会基于**所有同名属性**进行连接，从而可能引入意外的连接条件，导致结果缺失。

具体来说，在典型的大学数据库模式中，这几个表的常见结构如下：

- `instructor`：ID, name, **dept_name**, salary
- `teaches`：ID, course_id, sec_id, semester, year
- `section`：course_id, sec_id, semester, year, building, room_number, …
- `course`：course_id, title, **dept_name**, credits

注意 `instructor` 和 `course` 表都包含 `dept_name` 列。当执行 `instructor natural join teaches natural join section natural join course` 时：

1. `instructor` 与 `teaches` 自然连接 —— 基于共同列 `ID`，结果包含 `instructor.dept_name`。
2. 再与 `section` 自然连接 —— 基于 `course_id, sec_id, semester, year`，此时 `dept_name` 仍然保留。
3. 最后与 `course` 自然连接 —— 由于此时中间结果既有 `course_id` 又有 `dept_name`（来自 instructor），而 `course` 表中也有 `course_id` 和 `dept_name`，自然连接会要求 **`instructor.dept_name = course.dept_name`** 作为额外的连接条件。

这导致只有那些**教师所属院系与课程开设院系相同**的授课记录才会被保留。如果存在跨系授课（比如计算机系教师教授数学系课程），这些记录会被错误地排除，查询结果将不完整。

**如何修复？** 用显式的 `JOIN ... USING` 或 `JOIN ... ON` 明确指定连接列，例如：

```sql
SELECT name, title
FROM instructor
JOIN teaches USING (ID)
JOIN section USING (course_id, sec_id, semester, year)
JOIN course USING (course_id)
WHERE semester = 'Spring' AND year = 2017;
```

## 4.4

假设我们有三个关系：r(A, B)、s(B, C) 和 t(B, D)，其中所有属性都声明为非空（not null）。
a. 请给出关系 r、s 和 t 的实例，使得在 (r natural left outer join s) natural left outer join t 的结果中，属性 C 具有一个空值，但属性 D 具有一个非空值。

要让 (r natural left outer join s) natural left outer join t 的结果中 C 为空且 D 不为空，我们需要让 r 中的数据在 s 中找不到匹配项（从而产生空的 C），但能在 t 中找到匹配项（从而产生非空的 D）。

具体实例构造如下：

- 关系 r(A, B) 包含一条记录： A=1, B=2
- 关系 s(B, C) 为空（不包含任何记录）： （无记录）
- 关系 t(B, D) 包含一条记录： B=2, D=3

执行过程验证：

1. 首先计算括号内的 r natural left outer join s：连接属性是 B。因为 s 是空的，r 中的 (1, 2) 在 s 中找不到匹配，所以保留 r 的记录，并将 C 补为空值。 中间结果为：(A=1, B=2, C=null)
1. 然后计算 中间结果 natural left outer join t：连接属性仍然是 B。中间结果中的 B=2，在关系 t 中可以找到匹配的记录 (B=2, D=3)。 最终结果为：(A=1, B=2, C=null, D=3)

在这个结果中，C 是空值，且 D 是非空值，完美满足题目要求。

b. 是否存在 r、s 和 t 的实例，使得在 r natural left outer join (s natural left outer join t) 的结果中，C 有一个空值，但 D 有一个非空值？请解释为什么存在或为什么不存在。

答案：不存在。

解释为什么不存在： 在表达式 r natural left outer join (s natural left outer join t)中，由于有括号，计算顺序发生了改变。

1. 先计算括号内部的连接：Temp = s natural left outer join t。 因为题目已知条件中，所有关系的属性都声明为非空（not null）。所以基础表 s 里的 B 和 C 都是非空的。 当 s 左外连接 t 时，结果集 Temp 中的每一条记录都是以 s 表的记录为基础的。因此，Temp 结果集中的属性 C 绝对不可能出现空值。

1. 再计算外面的连接：r natural left outer join Temp。 此时是以 r 为左表，Temp 为右表进行左外连接，连接条件是属性 B。 对于 r 中的每一条记录，只可能出现两种情况：

- 情况一：在 Temp 中找到了匹配的记录。 那么它就会把 Temp 中的 C 和 D 拿过来。因为前面已经证明了 Temp 中的 C 全部是非空的，所以此时结果中的 C 一定是非空值。
- 情况二：在 Temp 中没有找到匹配的记录。 根据左外连接的规则，右表（Temp）提供的所有属性都要补为空值。也就是说，C 和 D 会同时被设为空值（null）。

结论： 无论数据怎么变化，最终结果里的 (C, D) 要么是“C 非空”，要么是“C 和 D 都是空”。绝对不可能出现“C 为一个空值，但 D 为一个非空值”的情况。这也从侧面证明了，自然左外连接是不满足结合律的。

## 4.6

基于实践习题 3.2 中的查询，请展示如何定义视图 *student_grades* (ID, GPA)，它给出了每名学生的平均绩点；请回忆一下，我们用关系 *grade_points (grade, points)* 来把用字母表示的成绩等级转换为用数字表示的得分。请确保你的视图定义能够正确处理在 *takes* 关系的 *grade* 属性上取空 (null) 值的情况。

```sql
CREATE VIEW student_grades (ID, GPA) AS
SELECT student.ID, 
       SUM(course.credits * grade_points.points) / SUM(course.credits)
FROM student
LEFT JOIN (
    takes 
    JOIN course ON takes.course_id = course.course_id
    JOIN grade_points ON takes.grade = grade_points.grade
) ON student.ID = takes.ID
GROUP BY student.ID;
```

## 4.9

SQL 允许外码依赖引用同一个关系，如下所示：

create table manager
    (employee_ID    char(20),
     manager_ID     char(20),
     primary key employee_ID,
     foreign key (manager_ID) references manager(employee_ID)
     on delete cascade )

在此，employee_ID 是 manager 表的码，这意味着每位员工最多只有一位经理。外码子句要求每位经理也是一位员工。请准确解释当 manager 关系中一个元组被删除时会发生什么情况。

**当 `manager` 关系中一个元组被删除时，会发生级联删除（Cascading Delete），并且由于是自引用（外码引用自身），这种删除会产生递归的连锁反应。**

具体过程如下：

1. 假设你删除了某个员工的记录（例如经理 A）。
1. 数据库会检查 `manager` 表中所有 `manager_ID` 等于被删除员工的 `employee_ID` 的记录（即查找所有直接向经理 A 汇报的员工）。
1. 因为定义了 `on delete cascade`（级联删除），这些直接下属的记录也会被自动删除。
1. **最关键的是：** 这个过程是递归的。当直接下属的记录被删除时，系统会继续寻找这些下属的下属，并将他们也删除。
1. **最终结果：** 删除任何一个员工的元组，将会自动删除该员工的所有直接下属、间接下属……直到整个由该员工领导的“管理树”分支上的所有员工元组都被彻底删除。

## 4.10

给定关系 a(name, address, title) 和 b(name, address, salary)，请展示如何使用带 on 条件的全外连接（full outer-join）运算来表达 a 自然全外连接（natural full outer join）b，而不使用自然连接（natural join）语法。这可以使用合并（coalesce）运算来完成。请确保结果关系不包含 name 和 address 属性的两个拷贝，并且即使在 a 和 b 中的某些元组对于 name 或 address 属性取空值的情况下，所给出的解决方案也是正确的。

```SQL
SELECT 
    COALESCE(a.name, b.name) AS name,
    COALESCE(a.address, b.address) AS address,
    a.title,
    b.salary
FROM 
    a 
FULL OUTER JOIN 
    b ON a.name = b.name AND a.address = b.address;
```

1. **连接条件：** `FULL OUTER JOIN ... ON a.name = b.name AND a.address = b.address` 执行全外连接，尝试将 `a` 和 `b` 中 `name` 和 `address` 完全相等的元组匹配起来。对于没有匹配上的元组（`a` 中独有的或 `b` 中独有的），也会保留在结果中，另一侧用 NULL 填充。
2. **合并同名列（去重）：** `NATURAL JOIN` 的一个核心特性是同名的连接列在结果集中只出现一次。普通的外连接会产生 `a.name`, `b.name`, `a.address`, `b.address` 四列。使用 `COALESCE(a.name, b.name) AS name` 可以完美解决这个问题。`COALESCE` 函数返回参数列表中第一个非空的值：
   - 如果记录匹配，`a.name` 和 `b.name` 相等，返回该值。
   - 如果是 `a` 中独有的记录（左外），`b.name` 为 NULL，返回 `a.name`。
   - 如果是 `b` 中独有的记录（右外），`a.name` 为 NULL，返回 `b.name`。
3. **处理空值（NULL）：** 即使 `a` 或 `b` 中的 `name` 或 `address` 本身为 NULL，该语句依然正确。
   - 如果 `a` 中某行 `name` 是 NULL 且没有匹配到 `b`，结果中那行的 `a.name` 为 NULL，`b.name` 也因未匹配而为 NULL。`COALESCE(NULL, NULL)` 依然正确返回 NULL，忠实地保留了原始数据结构，不会因为空值而报错或产生多余的列拷贝。

## 4.11

操作系统通常只为数据文件提供两种类型的授权控制：读访问和写访问。为什么数据库系统提供这么多种授权？

数据库的操作语义远复杂于文件的“读/写”。  

- **文件**是无结构的字节流，只需控制**读**和**写**就够了。  
- **数据库**管理的是结构化、关联的数据，必须对**查询、插入、删除、更新、引用、执行、修改结构**等不同操作分别授权，才能实现最小权限和业务安全需求。

## 4.12

假设一个用户想授予另一个用户一个关系上的选择（select）访问权限。为什么该用户应该在授权（grant）语句中包含（或不包含）granted by current role 子句？

包含或不包含 `GRANTED BY current_role` 的关键区别在于**权限的归属和级联撤销行为**：

- **包含该子句**：授权以当前角色（`current_role`）的身份发出。这样，一旦该角色被撤销或其权限被回收，这次授予的权限也会被自动级联撤销，便于统一、动态地管理一组用户的权限。
- **不包含该子句**：授权以用户自身的身份发出，权限独立于角色。即使之后角色变动，已授予的权限依然保留，更适合需要长期稳定、不随角色变化而消失的场景。

- **回答：** **不需要。**
- **原因：** 视图的主要作用之一就是**安全性和数据隐藏**。数据库管理员可以通过创建视图，只暴露基础表（关系 r）中的部分行或列给特定用户。如果要求用户必须对底层关系 r 拥有 select 权限才能查询视图 v，那么该用户就可以直接去查询 r，从而绕过视图的安全限制，这使得视图的安全控制机制变得毫无意义。因此，用户只需要对视图 v 有 select 权限即可，DBMS 在执行时会依据视图创建者（或所有者）的权限去访问底层表 r。
